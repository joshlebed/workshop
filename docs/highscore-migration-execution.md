# HighScore migration — execution plan

Companion to `docs/highscore-migration-plan.md` (the ratified high-level plan). This file
breaks the migration into **PRs** (agent-shippable code changes) and **operator actions**
(portal/console work or admin commands), ordered by dependency. Update the status column
as items land; delete this file when the migration is complete.

Conventions:

- `PR-x` = a pull request in this repo. `OP-x` = an operator action (browser portal work,
  or an admin CLI command an agent can run with elevation — marked _agent-runnable_).
- "Depends on" lists hard blockers only. Anything not listed can proceed in parallel.
- Every PR follows normal repo rules: green `Quality`, guards satisfied, squash-merged.

## Dependency graph (waves)

```
Wave 0  (parallel):  OP-1 Apple App ID ─→ OP-2 Services ID, OP-3 ASC listing shell
                     OP-4 Google OAuth clients
                     OP-5 EAS project init          PR-1 shared-package extraction
                     PR-2 backend multi-audience auth + CORS ─→ OP-6 SSM audience values
Wave 1:              PR-3 scaffold apps/highscore   (needs OP-1, OP-5, PR-1)
Wave 2:              PR-4 move games surfaces        (needs PR-3)
                     PR-5 CI generalization          (needs PR-3)
Wave 3a (web):       OP-7 CF Pages project ─→ PR-6 highscore functions/OG/AASA
                     ─→ OP-8 attach highscore.live ─→ PR-7 deploy-verify both domains
Wave 3b (iOS):       PR-8 testflight-highscore + guards (needs PR-4, OP-3)
                     ─→ TestFlight validation ─→ OP-9 App Store submission
Wave 4  (cutover):   OP-10 user notification ─→ PR-9 workshop games-tab cutover + redirects
                     (needs App Store listing LIVE)
Wave 5  (cleanup):   PR-10 delete dead code + docs sweep    OP-11 branch protection   OP-12 Google consent-screen split (later)
```

Waves 3a and 3b are independent of each other. Everything inside a wave is parallel
unless an arrow says otherwise.
